# Current design decisions

The [architecture diagram](architecture.canvas) shows how a request moves from submission through execution, verification and reporting, and the [formal specification](FORMAL_SPEC.md) defines the verified state-machine invariants and boundedness properties.

| Decision | Rule |
|---|---|
| Product and identity | One root Rust crate and one `teamagents` binary. Chat and exec use the same local daemon. `default` is an ordinary execution agent. The user can select the first agent when submitting work. |
| Execution tree | Each session starts in a fresh root with per-node conversation histories (`node_messages`), never inheriting prior sessions' context. New roots prepend hierarchical `AGENTS.md`/`AGENTS.override.md`, local `SKILL.md` index metadata, and git/environment context into the task prefix. Within a round, only the active subtree root stage may ask the user for clarification before starting work. `Root` and `Node` workers may issue parallel single-turn tool batches (up to 16 calls per turn: read-only tools execute concurrently while side-effecting tools execute sequentially) or solo control actions (`finish`, `handoff`, `ask`, `wb_wait`, `spawn`, `delegate`, `send`), plus `update_plan` progress, V4A `apply_patch`, `list_dir`, `grep_files`, `read_file(line_numbers)`, `read_skill`, and MCP (`mcp_list`, `mcp_call`). Live SSE reasoning/commentary and shell tail output stream transiently via `live`/`live_children`, and `steer` injects user guidance before the next model turn. Each member takes at most one stage per `(root, round)` and may participate again in subsequent continuation rounds. Only forward handoffs are allowed within a round. |
| Convergence & continuation | A round that settles with **1 terminal leaf** skips the summarizer and completes directly at that leaf (`continuation_node = leaf_id`). A round with **2+ terminal leaves** converges into an in-tree `summarizer` node (`kind = "summarizer"`, internal agent) receiving original/round intent (up to 8 MiB), clarifications, terminal leaf results (up to 2 MiB), a read-only `whiteboard` snapshot (treated as unverified notes), aggregate work outcome and verification status without workspace tools or private worker histories (`continuation_node = summarizer_id`). Follow-up user input (`continue TASK_ID TEXT` or composer input on the settled sole leaf / summarizer) promotes that continuation node to the next round's subtree root, unless `outcome == "unknown"`. Per-root whiteboard entries persist across continuation rounds until deleted with the root. |
| Collaborative whiteboard | Each root owns persistent `whiteboard_entries` (`note`, `contract`, `claim`, `question`, `decision`) with monotonic `seq`, per-entry `version` CAS checks (`expected_version`), and single-writer serialized `append`, `resolve` and `delete`. Entries are capped at 64 KiB each and 1 MiB per root. Active `root` and `node` workers may call `wb_read`, `wb_write` and `wb_wait`; `wb_wait` wakes on a matching write or delete, or immediately with `no_other_writers` when no non-waiting writers remain in the round, but can remain asleep while a sibling is parked on human approval. A newest-first unread digest (<= 4 KiB) injects transiently at claim when `wb_seq` advances past the node's explicit seen watermark; claiming alone does not advance that watermark. A batched read advances it only when the delivered receipt covers the unread range and includes every matching entry. A CAS conflict records a failed write receipt and preserves the board sequence. Users inspect and mutate whiteboards via `teamagents whiteboard` (`wb`), `/wb`, and the TUI `Board` tab. |
| Session | The canonical workspace selects a hashed session under `${XDG_STATE_HOME:-$HOME/.local/state}/teamagents-swarm/sessions`. An explicit `--session` is a directory bound to its workspace. It must be owned by the user, disjoint from the workspace and writable only by the owner. |
| Session protocol and recovery | The client verifies wire protocol 3 before sending a mutation and checks the provider before submitting work or accessing model settings. Clients negotiate `provider_switching` and `codex_v1` on `hello`, enabling `submit_full`/`continue_full` (`sandbox`), `steer`, `compact`, `diff`, `skills`, `mcp`, and `files`, while explicit `TEAMAGENTS_PROVIDER` env mismatches are still rejected on unacknowledged `submit`/`continue` without submitting work. Store v10 adds `operations.batch_id`/`seq_idx`/`call_id`, `tree_runs.plan_json`, the `steerings` table, and `root_policies.sandbox`; it preserves each root's routing, approval policy, sandbox mode (`direct`, `staged`, or `read_only`), active session provider override, and pending operations on reopen. Stored roots without an explicit policy require per-operation review. Waiters parked on `wb_wait` with no live writers wake cleanly on recovery. |
| Authority | Unattended is the default for new roots. `--review` on `exec`, `continue`, `review`, `chat` or `tui` requires a user decision on each pending model-requested edit or shell command. It binds the exact operation and its `approval_id`. Descendants inherit the root policy. Prompts, agents and tool output cannot change it. |
| Shell and checks | Both use `/usr/bin/bwrap` and `/usr/bin/slirp4netns` on Linux with namespaces permitted. New roots default to direct `workspace-write` bind mounts (hiding the top-level `.teamagents-auth` entry and protecting top-level Git admin dirs read-only; native tools reject nested reserved paths recursively); `--staged` / `--sandbox staged` opts into a staged workspace copy with validated publication; `--sandbox read-only` mounts `/workspace` read-only in `bwrap` and disables `edit_file`/`apply_patch`. Descendants inherit the root's sandbox mode. Shell output streams live chunks into transient `LiveActivity.shell_tail`. Do not mount host home, credential stores or the daemon socket. Loopback is sandbox-private. |
| Publication | In `--staged` mode, shells stage directories and single-link regular files (256 MiB, 32,768 entries, depth 64), refusing links, special files and nested mounts while skipping Git metadata and marked Cargo target caches, and validate a host snapshot before per-entry writeback plus recheck each entry immediately before publish, even on nonzero exit. External writers need not honor the workspace flock; multi-file publication is not atomic and a crash can leave partial writes. Native `edit_file`/`apply_patch` write the direct host workspace and are not staged. Direct mode writes straight to workspace files inside `bwrap` without staging caps. |
| Acceptance and repair | A checked root may succeed only after the exact user-supplied `exec --check COMMAND` passes. After a failure, the daemon can create a new repair stage with the diagnostics. Earlier stages stay closed. At most ten check attempts total. An unchecked root remains `verification: "not_requested"` even when a model-requested command succeeded. |
| Inspection and clarification | Root `status` covers the whole run. `stage_status` tracks its own execution stage. Root status exposes `tree_nodes`, `leaf_results`, `whiteboard_seq`, `whiteboard` and a `subtree_receipts` index. Full operation `evidence` belongs to the individual task. In state `input`, inspect `question` and reply with `answer ROOT_ID TEXT` or `/answer ROOT_ID TEXT` in chat. |
| Aggregate outcome | Siblings settle independently. Once all settle, an unknown operation takes precedence. A failed or cancelled branch yields `failed` for the run. Cancelling the whole root yields `cancelled` unless an operation has an unknown outcome. Leaf statuses remain available. |
| Clients | `exec`, `continue`, `review`, and `resume` wait for a final result or print a clarification and exit with a nonzero status; bare `resume` selects the newest root when no ID is given, opens the TUI on an interactive terminal, and uses the line client with `--json`, `--jsonl`, `--timeout` or `--detach`; while `resume TASK_ID TEXT` continues it. `--detach` returns the receipt; `--timeout SECONDS` bounds only client wait; `--jsonl` emits live JSONL events (`submitted`, `live`, `plan`, `input`, `approval`, `completed`); `--sandbox direct|staged|read-only` selects the sandbox mode. `steer`, `compact`, `diff`, `skills`, `mcp [list|add|remove|tools]`, and `whiteboard` (`wb`) manage active guidance, manual compaction, workspace diffs, discovered skills, MCP servers, and collaborative whiteboards. On an interactive TTY, `chat` (without `--plain` or `--json`) and `tui` launch the TUI with `@file` fuzzy completion, `/sandbox`, `/plan`, `/review code`, `/diff`, `/steer`, `/compact`, `/skills`, `/mcp`, and `/status`; non-TTY I/O, `--plain`, and `--json` use the line-oriented client. |
| Durability | One daemon writes a session's SQLite store using WAL and `synchronous=FULL`. Model and tool I/O occur outside write transactions. A started operation without a durable result has an unknown outcome and cannot be replayed automatically or continued without user inspection. Cancellation cannot roll back effects. |
| Limits | No model turn budget, session member cap, concurrency cap, same-agent serialization, or history message-count limit. Runtime payload and execution bounds are up to `16` tool calls per parallel turn batch, `64` children per handoff, `10` check attempts, `5` consecutive protocol-error action rejections per worker node round (resetting on each accepted action), `8 MiB` `edit_file`/`apply_patch` & unpaginated `read_file` slice, `1 MiB` stored per-tool-result cap with an explicit truncation marker, `128 KiB` middle-truncated per-stream shell output (`64 KiB` head + `64 KiB` tail), model-controllable shell `timeout_ms` (`100..=600_000` ms, default `60s`), `8 MiB` worker request (`2 MiB` response; `12 MiB` reporter request), automatic & manual context compaction (byte-estimated `90%` of context window within the `8 MiB` ceiling with >= 4 persisted messages, preserving tool-call pairs; not a tokenizer measurement), `32 MiB` SSE stream, `8 MiB` IPC frame, `2 MiB` leaf / `8 MiB` intent summarizer inputs, `4 KiB` whiteboard digest, `1000` TUI events / workspace `@` index entries, MCP config `256 KiB` / `30s` RPC timeout / `2 MiB` response cap, and `30s` quota circuit-breaker. |
| Provider | Built-in providers (`deepseek`, `chatgpt`, `api`, `responses`, `anthropic`) plus user-configured custom providers in `${XDG_CONFIG_HOME:-$HOME/.config}/teamagents/providers.json` (`TEAMAGENTS_PROVIDERS_FILE` override), managed via `teamagents provider [list|show|add|remove|default]` and `/provider ...`. Custom providers support `responses`, `chat_completions`, and `anthropic` wires, store only credential environment variable names (`api_key_env`, never plaintext API keys), enforce HTTPS + `api_key_env` off loopback, and cannot override built-in names or use `chatgpt` OAuth. MCP server configs in `${XDG_CONFIG_HOME:-$HOME/.config}/teamagents/mcp.json` (`TEAMAGENTS_MCP_FILE` override) follow the same env-var-only credential hygiene (`env_vars`, `bearer_token_env`). `TEAMAGENTS_PROVIDER` (or `default_provider`) sets the initial session default; without an override the daemon prefers `deepseek` whenever `DEEPSEEK_API_KEY` is set, else ChatGPT OAuth, else `anthropic`, else `api`. All providers supply the parallel tool schema (`parallel_tool_calls: true`, Anthropic `tool_choice: {"type":"any"}`), streaming SSE callbacks, static prefix + identity-last layout for prompt caching, default context fork across `handoff`, and per-node/root `usage` telemetry. |
| Model selection | `/model` (and `/model provider NAME [MODEL [EFFORT]]`, `/model providers`, `/provider use NAME`, or the TUI `/model` provider bar) switches active provider, model, and reasoning effort live on a running daemon for subsequent new roots and continuations without restarting. Store v9 adds `settings.active_provider` and `root_model_settings.provider`; per-provider `model_overrides` and `root_model_settings` themselves date from v4. Together they persist session-level `active_provider`, per-provider `model_overrides`, and snapshots `(provider, model, effort)` at submission/continuation so already-running or earlier roots remain pinned across switches and daemon restarts. |
| Delivery | Install from a reviewed checkout with Cargo's lockfile, or unpack a host binary archive. Install sandbox dependencies separately. CI uses the pinned Rust toolchain and requires working sandbox tests. Publishing requires a matching version-tag push and `TEAMAGENTS_RELEASE_APPROVED=true`. |
