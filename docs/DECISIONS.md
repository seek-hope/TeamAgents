# Current design decisions

The [architecture diagram](architecture.canvas) shows how a request moves from submission through execution, verification and reporting, and the [formal specification](FORMAL_SPEC.md) defines the verified state-machine invariants and boundedness properties.

| Decision | Rule |
|---|---|
| Product and identity | One root Rust crate and one `teamagents` binary. Chat and exec use the same local daemon. `default` is an ordinary execution agent. The user can select the first agent when submitting work. |
| Execution tree | Each session starts in a fresh root with per-node conversation histories (`node_messages`), never inheriting prior sessions' context. Within a round, only the active subtree root stage may ask the user for clarification before starting work. A stage can use tools, read/write/wait on the collaborative whiteboard, finish as a leaf or hand off up to 64 assignments atomically. Named workers join on demand without a session member limit, concurrency limit, or same-agent serialization. Each member takes at most one stage per `(root, round)` and may participate again in subsequent continuation rounds. Only forward handoffs are allowed within a round. A descendant cannot wake an ancestor or route work to a sibling. |
| Convergence & continuation | A round that settles with **1 terminal leaf** skips the summarizer and completes directly at that leaf (`continuation_node = leaf_id`). A round with **2+ terminal leaves** converges into an in-tree `summarizer` node (`kind = "summarizer"`, internal agent) receiving original/round intent (up to 8 MiB), clarifications, terminal leaf results (up to 2 MiB), a read-only `whiteboard` snapshot (treated as unverified notes), aggregate work outcome and verification status without workspace tools or private worker histories (`continuation_node = summarizer_id`). Follow-up user input (`continue TASK_ID TEXT` or composer input on the settled sole leaf / summarizer) promotes that continuation node to the next round's subtree root, unless `outcome == "unknown"`. Per-root whiteboard entries persist across continuation rounds until deleted with the root. |
| Collaborative whiteboard | Each root owns persistent `whiteboard_entries` (`note`, `contract`, `claim`, `question`, `decision`) with monotonic `seq`, per-entry `version` CAS checks (`expected_version`), lock-free `append`, `resolve` and `delete`. Active `root` and `node` workers may call `wb_read`, `wb_write` and deadlock-free `wb_wait` (which wakes on matching updates or immediately with `no_other_writers` when no non-waiting writers remain in the round). A compact digest (<= 4 KiB) injects transiently into focus turns on `claim`. Users inspect and mutate whiteboards via `teamagents whiteboard` (`wb`), `/wb`, and the TUI `Board` tab. |
| Session | The canonical workspace selects a hashed session under `${XDG_STATE_HOME:-$HOME/.local/state}/teamagents-swarm/sessions`. An explicit `--session` is a directory bound to its workspace. It must be owned by the user, disjoint from the workspace and writable only by the owner. |
| Session protocol and recovery | The client verifies wire protocol 3 before sending a mutation and checks the provider before submitting work or accessing model settings. Reopening a session preserves each root's routing, approval policy, sandbox mode (`direct` or `staged`) and pending operations. Stored roots without an explicit policy require per-operation review. Waiters parked on `wb_wait` with no live writers wake cleanly on recovery. |
| Authority | Unattended is the default for new roots. `--review` on `exec`, `continue`, `chat` or `tui` requires a user decision on each pending model-requested edit or shell command. It binds the exact operation and its `approval_id`. Descendants inherit the root policy. Prompts, agents and tool output cannot change it. |
| Shell and checks | Both use `/usr/bin/bwrap` and `/usr/bin/slirp4netns` on Linux with namespaces permitted. New roots default to direct `workspace-write` bind mounts (hiding `.teamagents-auth` and protecting top-level Git admin dirs read-only); `--staged` opts into a staged workspace copy with validated publication. Descendants inherit the root's sandbox mode. Do not mount host home, credential stores or the daemon socket. Loopback is sandbox-private. Shell traffic may transmit workspace material externally or reach LAN services. Provider traffic originates separately in the daemon. |
| Publication | In `--staged` mode, shells stage directories and single-link regular files (256 MiB, 32,768 entries, depth 64), refusing links, special files and nested mounts while excluding Git metadata and marked Cargo target caches, and validate changes and conflicts before per-entry writeback, even on nonzero exit. Multi-file publication is not atomic. Direct mode writes straight to workspace files inside `bwrap` without staging caps. |
| Acceptance and repair | A checked root may succeed only after the exact user-supplied `exec --check COMMAND` passes. After a failure, the daemon can create a new repair stage with the diagnostics. Earlier stages stay closed. At most ten check attempts total. An unchecked root remains `verification: "not_requested"` even when a model-requested command succeeded. |
| Inspection and clarification | Root `status` covers the whole run. `stage_status` tracks its own execution stage. Root status exposes `tree_nodes`, `leaf_results`, `whiteboard_seq`, `whiteboard` and a `subtree_receipts` index. Full operation `evidence` belongs to the individual task. In state `input`, inspect `question` and reply with `answer ROOT_ID TEXT` or `/answer ROOT_ID TEXT` in chat. |
| Aggregate outcome | Siblings settle independently. Once all settle, an unknown operation takes precedence. A failed or cancelled branch yields `failed` for the run. Cancelling the whole root yields `cancelled` unless an operation has an unknown outcome. Leaf statuses remain available. |
| Clients | `exec` and `continue` wait for a final result or print a clarification and exit with a nonzero status. `--detach` returns the receipt; `--timeout SECONDS` bounds only client wait; `--staged` selects staged sandbox execution. `whiteboard` (`wb`) inspects or modifies a root's collaborative whiteboard. On an interactive TTY, `chat` (without `--plain` or `--json`) and `tui` launch the TUI; non-TTY I/O, `--plain`, and `--json` use the line-oriented client. Opening `chat` or `tui` always enters a fresh new session (`Ctrl+N` / `+New` / `/new` returns to a blank session, while historical sessions stay accessible in the sidebar and can be deleted via `Del`×2). In a settled session with a sole leaf or summarizer node, plain input continues directly from that node as the next subtree root; while clarification waits on the selected root, plain text answers it (`/answer ROOT_ID TEXT` explicitly selects a question; `/new TEXT` starts a separate root). Leaving the client keeps work running. |
| Durability | One daemon writes a session's SQLite store using WAL and `synchronous=FULL`. Model and tool I/O occur outside write transactions. A started operation without a durable result has an unknown outcome and cannot be replayed automatically or continued without user inspection. Cancellation cannot roll back effects. |
| Limits | No model turn budget, session member cap, concurrency cap, same-agent serialization, or history message-count limit. Runtime payload and execution bounds are up to `64` children per handoff, up to `10` check attempts, up to `5` consecutive protocol-error action rejections per worker node round (resetting on each accepted action), `8 MiB` `edit_file` & unpaginated `read_file` slice (paginated via `offset`/`limit` beyond `8 MiB`), `128 KiB` middle-truncated per-stream shell output (`64 KiB` head + `64 KiB` tail), model-controllable shell `timeout_ms` (`100..=600_000` ms, default `60s`, `exit 124` on timeout), `2 MiB` worker request/response/action text (`12 MiB` reporter request), automatic context compaction (`384 KiB` soft trigger with >= 6 messages or context-overflow / HTTP 413 fallback via provider summarization / `32 KiB` deterministic fallback, preserving tool-call pairs across splits), transient repetition nudges for consecutive duplicate or repeated read-only `shell` probes, `32 MiB` Responses/Anthropic SSE stream, `8 MiB` IPC frame, `2 MiB` leaf output / `8 MiB` intent summarizer inputs, `4 KiB` whiteboard digest, `30s` shared quota-exhaustion pause circuit-breaker, and `1000` TUI events. Provider token charges still apply per call. |
| Provider | `TEAMAGENTS_PROVIDER` supports `chatgpt`, `api` (OpenAI Chat Completions), `responses` (OpenAI Responses API), and `anthropic` (Anthropic Messages API). All four providers supply native typed tool schemas enforcing single-action-per-turn semantics while keeping raw JSON text fallback, and replay historical paired tool interactions natively (`function_call` + `function_call_output` for Responses/ChatGPT, `tool_calls` + `tool` for Chat Completions, `tool_use` + `tool_result` for Anthropic when thinking is disabled; plain text fallback under Anthropic extended thinking). `chatgpt` requires the user's ChatGPT plan, uses OpenAI's PKCE OAuth flow, and sends tokens only to the official OpenAI API. `responses` uses `OPENAI_BASE_URL` / `OPENAI_API_KEY` (`/responses`, streaming SSE or JSON); `api` uses `/chat/completions`; `anthropic` uses `ANTHROPIC_BASE_URL` / `ANTHROPIC_API_KEY` (`/v1/messages`, `x-api-key`, `anthropic-version: 2023-06-01`, optional `ANTHROPIC_MODEL` and `ANTHROPIC_MAX_TOKENS`, coalesced alternating messages, and `thinking` budget mapping). Without an override the daemon prefers a signed-in ChatGPT plan, then Anthropic if only `ANTHROPIC_*` env vars are set, else `api`. Responses decoding reconciles native `function_call` items (including preceding commentary/narration), skips `phase: "commentary"` assistant messages before the final answer, and treats missing/multi-tool/refusal/malformed items as retryable `InvalidAction` protocol corrections (up to 5 consecutive rejections per round, resetting on accepted actions). Model HTTP requests use `600s` read timeout (`30s` connect, `60s` write), follow up to 5 redirects, coordinate rate-limit waits across workers, and retry transient transport, 408, 429, 5xx, 529, and transient stream errors up to 5 attempts total. Quota exhaustion triggers a `30s` pause circuit-breaker across in-flight turns (cleared on new `submit` or `continue`). |
| Model selection | `/model` selects the model and reasoning effort for new chat and exec roots in the current session. Store session overrides per provider and snapshot effective settings at submission for the entire tree, including repair and reporting. A default effort omits the request field so the provider chooses. |
| Delivery | Install from a reviewed checkout with Cargo's lockfile, or unpack a host binary archive. Install sandbox dependencies separately. CI uses the pinned Rust toolchain and requires working sandbox tests. Publishing requires a matching version-tag push and `TEAMAGENTS_RELEASE_APPROVED=true`. |
