# Current design decisions

The [0.5.0 canvas](teamagents-0.5.0.canvas) shows the execution and reporting paths.

| Decision | Rule |
|---|---|
| Product and identity | One root Rust crate and one `teamagents` binary. Chat and exec use the same local daemon. `default` is an ordinary execution agent. The user can select the first agent when submitting work. |
| Execution tree | Each new root starts with one execution stage. Only that first stage may ask the user for clarification before starting work. A stage can use tools, finish as a leaf or hand off up to 16 assignments. A handoff closes the sender and creates all children atomically. Named workers join on demand within the session's member limit. Each member takes at most one stage per tree. Each child receives the sender's stage summary and its own assignment. Only forward handoffs are allowed. A descendant cannot wake an ancestor or route work to a sibling. |
| Reporting | A summarizer outside the execution tree receives the original intent, clarifications, terminal leaf results, aggregate work outcome and verification status. It has no workspace tools or private agent histories. Its only action is to finish the report. With a root budget greater than one, execution leaves the last call for reporting. If there is no usable model report, the runtime returns a deterministic partial report and marks an otherwise successful run `failed`. The root ID stays valid after its first stage closes. |
| Session | The canonical workspace selects a hashed session under `${XDG_STATE_HOME:-$HOME/.local/state}/teamagents-swarm/sessions`. An explicit `--session` is a directory bound to its workspace. It must be owned by the user, disjoint from the workspace and writable only by the owner. |
| Session migration | The client verifies wire protocol 3 before sending mutating requests. Migration preserves routing, approval policy and pending operations for existing roots and their descendants. Schema 1 roots keep per-operation review. New roots use the one-way tree in every session. |
| Authority | Unattended is the default for new roots. `--review` on `exec` or `chat` requires a user decision on each pending model-requested edit or shell command. It binds the exact operation and its `approval_id`. Descendants inherit the root policy. Prompts, agents and tool output cannot change it. |
| Shell and checks | Both use `/usr/bin/bwrap` and `/usr/bin/slirp4netns` on Linux with namespaces permitted. Run in a staged workspace and validate before publishing changes. Do not mount host home, credential stores or the daemon socket. Loopback is sandbox-private. Shell traffic may transmit workspace material externally or reach LAN services. Provider traffic originates separately in the daemon. |
| Publication | Shells stage directories and single-link regular files (256 MiB, 32,768 entries, depth 64). Refuse links, special files and nested mounts. Exclude Git metadata and marked Cargo target caches. Validate the completed command's changes and check for conflicts before per-entry writeback, even on nonzero exit. Multi-file publication is not atomic. |
| Acceptance and repair | A checked root may succeed only after the exact user-supplied `exec --check COMMAND` passes. After a failure, the daemon can create a new repair stage with the diagnostics, even when the persistent roster is full. Earlier stages stay closed. At most three check attempts total, subject to the remaining shared root budget. An unchecked root remains `verification: "not_requested"` even when a model-requested command succeeded. |
| Inspection and clarification | Root `status` covers the whole run. `stage_status` tracks its own execution stage. Root status exposes `tree_nodes`, `leaf_results` and a `subtree_receipts` index. Full operation `evidence` belongs to the individual task. In state `input`, inspect `question` and reply with `answer ROOT_ID TEXT` or `/answer ROOT_ID TEXT` in chat. |
| Aggregate outcome | Siblings settle independently. Once all settle, an unknown operation takes precedence. A failed or cancelled branch yields `failed` for the run. Cancelling the whole root yields `cancelled` unless an operation has an unknown outcome. Leaf statuses remain available. |
| Clients | `exec` waits for a final result or prints a clarification and exits with a nonzero status. `--detach` returns the receipt. Optional `--timeout SECONDS` bounds only the client wait. The root has no wall-clock deadline. In chat, plain text can answer a single pending question for the selected agent. `/new TEXT` explicitly starts separate work. Leaving the client keeps the root available by ID. |
| Durability | One daemon writes a session's SQLite store using WAL and `synchronous=FULL`. Model and tool I/O occur outside write transactions. A started operation without a durable result has an unknown outcome and cannot be replayed automatically. Cancellation cannot roll back effects. |
| Limits | Session creation sets `TEAMAGENTS_MAX_AGENTS` (default 8 including `default`) and `TEAMAGENTS_TURN_BUDGET` (default 32 model calls per root including descendant, repair and summarizer turns). Daemon startup sets `TEAMAGENTS_CONCURRENCY` (default 4). Provider token charges vary per call. |
| Provider | `TEAMAGENTS_PROVIDER=chatgpt` requires the user's ChatGPT plan. `auth login` uses OpenAI's native public-client OAuth flow with PKCE and a loopback callback. The daemon sends the plan token only to the official OpenAI API, selects a visible model if needed and validates the completed Responses stream before acting. `TEAMAGENTS_PROVIDER=api` selects OpenAI-compatible Chat Completions using a model ID from `/model` or `TEAMAGENTS_MODEL`, `OPENAI_BASE_URL` and `OPENAI_API_KEY` (optional on loopback). Without an override the daemon prefers a signed-in plan. The selected provider stays fixed for the process. Keep credentials outside workspaces and session databases, including during token rotation. Disable redirects and automatic inference retries. |
| Model selection | `/model` selects the model and reasoning effort for new chat and exec roots in the current session. Store session overrides per provider and snapshot effective settings at submission for the entire tree, including repair and reporting. A default effort omits the request field so the provider chooses. |
| Delivery | Install from a reviewed checkout with Cargo's lockfile, or unpack a host binary archive. Install sandbox dependencies separately. CI uses the pinned Rust toolchain and requires working sandbox tests. Publishing requires a matching version-tag push and `TEAMAGENTS_RELEASE_APPROVED=true`. |
