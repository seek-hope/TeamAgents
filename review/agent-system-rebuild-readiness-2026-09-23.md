## 1. [P1] 制品发布与回收之间缺少保护，可能形成悬空引用

位置：方案 §4.3 L138、§4.4 L146、§9 L261；影响 R03/R08/R09，现有 A30/A31/A32。

方案正确地要求“先发布持久化文件，再提交数据库引用”，并允许清理孤儿文件。但“没有已提交引用”不等于“已经是孤儿”，当前没有定义尚在发布中的制品如何被回收器识别：

1. 完整响应文件发布，生产者尚未提交其数据库引用。
2. 回收器查不到引用，删除该文件。
3. 生产者提交引用，恢复时读到不存在的响应文件。

另一种顺序是后台重启后，回收先于“已发布完整响应的核验导入”运行。只保护活动的已提交引用、给文件设置一个固定宽限时间，都不能完整排除这些窗口。

探针 `artifact_publication_gc` 使用实际临时文件和 SQLite，强制排列上述步骤：无发布保护时引用已提交而文件不存在；不运行 GC 的对照、预先登记 pending 所有者的对照均保留文件。这证明的是原子边界需要一个明确合约，不是断言所有实现必然采用错误回收算法。

建议补入 §4.3/§4.4：

- 文件发布前登记稳定制品身份及发布中的所有者/保护记录，绑定 request/operation；引用提交与保护转移在同一事务内完成。
- GC 只能处理无活动所有者、无发布保护、无保留证据引用的对象，并与发布/新增引用串行协调；不能仅扫描“文件有、引用无”。
- runner 独立写出的结果目录在回执核验导入前受对应 job 保护。重启先核对这些记录，再回收。
- 首个探针阶段也可先只允许停稳后的离线 GC；若采取该简化，明确禁止运行中 GC，不能只靠延迟猜测。

补充验收：发布与 GC 交错、GC 已选中候选后新建引用、发布后崩溃再启动 GC、runner 已写结果但未导入。每个提交成功的引用都必须可读取，且失败发布留下的真实孤儿最终可回收。

## 2. [P1] GO 去重不等于取消后禁止启动，runner 需要持久化取消状态

位置：方案 §6.2 L190、§6.3 L206、§6.4 L216；影响 R03/R11/R12，现有 A10/A11/A13。

当前协议定义了 READY、派发提交、GO 和重复 GO 去重；取消定义为落盘后终止进程组。缺少的分支是：**取消到达时，命令尚未创建进程组，但启动授权已经提交。**

可能的顺序：

1. runner READY，数据库记录 DISPATCH_COMMITTED，GO 在途。
2. 用户取消，runner 收到取消时还没有子进程。
3. 原 GO 迟到，或后台恢复依据“派发已提交”重发 GO。
4. 如果 runner 只记“GO 是否执行过”、没有记录“不许再开始”，命令仍会启动。

这不是重复执行问题：总共只启动一次，也仍然可能违背已经处理的取消。已有“操作终态唯一”的数据库约束也不能代替独立 runner 的启动闸门。不能据一次“没有 PID”把取消确认为最终停止。

探针 `cancel_before_go_model` 是协议状态模型：在先 CANCEL 后两次 GO 的序列中，仅去重会启动一次；具有取消终态的对照启动零次。它未模拟真实 IPC，也不证明 runner 的实现已经存在该错误。

建议补入 §6：

- runner 为同一 job 串行处理 GO/CANCEL，并持久化取消或其他禁止启动的终态；处于该状态的 job 永久拒绝后续 GO。
- 区分取消请求、runner 接受取消、确认未启动/确认进程组停止；明确每种回执的含义。
- 后台恢复读取最新目标/任务/操作控制状态，再决定发送 GO 还是 CANCEL。不能仅凭旧 DISPATCH_COMMITTED 记录重发。
- GO 先于 CANCEL 时记录真实执行效果并请求停止；不承诺撤销已经发生的效果。CANCEL 先被 runner 接受时不得再启动。
- 将此状态纳入启动标记之前/之后、取消记录之前/之后、IPC 丢失及重复消息的恢复矩阵。

补充验收：CANCEL→GO、GO→CANCEL、两者重复、取消后 daemon 重启、runner 重启以及无 PID 的启动窗口。原生进程测试确认取消已确认后没有新命令启动；无法确认时如实返回未确认状态。

## 3. [P1] 存储失效时不能让“先持久化取消”成为终止命令的唯一入口

位置：方案 §4.4 L146、§6.4 L216、A31 L346；影响 R03/R11/R12/R21。

“取消先落盘，再终止进程组”适用于正常存储，却没有磁盘满/写入失败的分支。若保存取消意图失败就提前返回，正在运行、可能继续写满磁盘的命令无法通过产品控制入口停止；仅停止新派发不能解决已有 job。

探针 `storage_failure_cancel`：

- 使用 SQLite 页面上限触发真实 `SQLITE_FULL`，没有填满主机磁盘。
- 创建一个专属测试进程组。按“存储成功才发终止信号”的顺序，写入失败后进程仍在运行。
- 通过独立控制路径发信号可停止同一进程；探针始终在 finally 中清理测试进程。

页面上限机制见 [SQLite 官方 PRAGMA 说明](https://sqlite.org/pragma.html#pragma_max_page_count)。探针使用 Python 自带 SQLite，不代表 TeamAgents 链接的 SQLite 版本；也不模拟实际介质损坏。

建议补入 §4.4/§6.4：

- 正常取消保持先落盘。存储失效时先冻结相关执行的新派发，同时保留经身份/进程核验的尽力停止通道；不能因为写回执失败而完全放弃停止。
- 将“进程已停止”“目标取消已持久化”分开报告。持久化失败时不能向用户伪报已保存取消。
- 资源策略为控制操作保留可用能力，限制/降级批量输出；该策略不能被描述为能战胜任意 I/O 故障。
- 明确重启后的保证边界：能恢复的取消记录或 runner 回执优先核对；所有可写存储均失效时，不能承诺记住未保存的取消。此时必须暴露失败和恢复风险，不能声称正常自动续跑等同于恢复了用户取消意图。

补充验收：取消日志写失败、runner 回执写失败、工具输出写失败，以及这些失败期间的暂停/取消和重启。测试同时检查执行停止效果与持久化状态，不把二者合并为一个成功布尔值。

## 5. 可在 P0/对应阶段确定的事项

这些事项无需重开产品需求访谈，但必须在相应阶段有具体产物：

- **后台配置与凭据来源**：daemon 长驻后，不能把 CLI 当前环境等同于 daemon 环境。R02/R04 明确环境变量何时读取、凭据配置如何刷新，以及 doctor 查询哪一端；结合 CLI 重连/更换模型检查。不能把密钥随普通事件或日志传送。该项目前作为实现注意事项，尚无新 daemon 的错误实现证据。
- **完整状态转移表**：R01 将目标终态、等待批准/用户、控制工具的结果配对、实例重置和迟到结果列成守卫与动作表。已有文字已包含方向，具体 Rust enum/SQL 约束是 P0 工作。
- **依赖、并发和性能精度**：继续按方案探针/试跑后确定；当前缺少吞吐数字不是架构错误。正式模型验收前必须冻结样本、预算、重复数和判据，不能边看结果边调整。
- **早期垂直贯通**：P0/R04 只做最小 TUI→后台→可观测任务→断开重连，P1/P2 优先验证单实例行为和恢复。其余能力按阶段加入，避免在首次真实闭环前搭完所有模块。
