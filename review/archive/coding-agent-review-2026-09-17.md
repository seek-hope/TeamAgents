# TeamAgents 编码能力审查与改进（2026-09-17）

本轮目标是提高真实编码任务的可靠性，并建立能够判断是否达到 Codex CLI、Claude Code、pi、Hermes 水平的证据。结论：TeamAgents 已有较完整的团队协调、权限、文件/Shell、持久恢复、协议适配与上下文能力；本轮发现的基础正确性缺陷说明，还不能仅凭功能数量或离线测试宣称达到这些产品的水平。

本轮已落码的修复均依据现有实现方案与 D-32，不引入新依赖，不改变 Rust 三 crate、事务权威、批准边界和成员身份。任务开始时用户已有的 `AGENTS.md`、`README.md`、`docs/DECISIONS.md`、`docs/USER-GUIDE.md` 修改未被覆盖。

## 已修复的主要问题

| 优先级 | 问题与实际影响 | 修复与证据 |
|---|---|---|
| P1 | 批量重构后一个文件失败，前面文件已经改动 | 全批预检、持有所有文件锁、暂存与失败回滚；[工具审查](review-coding-tools-2026-09-17.md) CT-01 |
| P1 | 读取 FIFO 阻塞在打开文件，取消无效 | 非阻塞打开，父路径限定目录类型；工具审查 CT-02 |
| P1 | 暂停会话后无法取消活动成员 | 暂停仅阻止新调度，仍处理取消；[运行审查](runtime-review-2026-09-17.md) |
| P1 | 迟到执行回执把 CANCELLED 改成 COMPLETED，或旧调度快照启动已取消回合 | 启动状态检查与终态保护；运行审查 |
| P1 | 声明完成后新增任务或用户要求，旧申请仍完成目标，甚至覆盖新目标 | 最终事务重验阻塞项与目标 ID，新输入使旧目标申请失效；[完成竞态审查](review-goal-completion-2026-09-17.md) |
| P1 | 模型截断响应仍执行工具或被视作正常回答 | 三类协议的 JSON/SSE 明确失败状态校验；[协议审查](model-protocol-review-2026-09-17.md) |
| P1 | Responses 无状态工具续接丢失推理项与 item ID | 保留原始输出顺序与不透明推理内容，跨协议移除内部字段；协议审查 |
| P1 | 评测任务失败，脚本却返回成功 | 校验实际退出码、最终记录、验收项、两个恢复阶段与空任务集；[能力与评测审查](capabilities-coding-agent-2026-09-17.md) |

批量编辑提供运行错误回滚，仍不是跨文件崩溃事务。外部 Shell/编辑器不遵守路径锁；回滚遇到外部修改或磁盘故障时，会报告恢复副本路径而不覆盖第三方修改。权限与取消修复也不能撤销已经产生的副作用。

## 验证与边界

新增 15 项 Rust 回归，最终 core **63** / engine **198** / TUI **91** 全部通过；engine 中 `live_codex` 的 1 项提前返回，不计入真实服务验收。真实 bubblewrap 下的文件/Shell 测试实际执行。两项 PTY 检查、评测入口 14 项无模型检查及 `git diff --check` 通过。

整合回归曾有一次 `process_leaks::codex_failed_initialize_reaps_the_child` 在执行新建临时脚本时返回 Linux `Text file busy`，尚未确定稳定复现条件；独立重跑与随后完整 engine 重跑通过。本轮没有通过修改业务逻辑掩盖这一测试环境波动，原日志保留在 `/tmp/teamagents-engine-transient-etxtbsy-20260917.log`。

真实 DeepSeek 5 类任务均符合预期：Rust 修复、精确编辑、团队协作、批准边界、中断后续接；协作在完成竞态修复前后各跑一次，两个结果都保留。恢复任务实际经历超时中断再继续，检查副作用不重复。没有调用真实 OpenAI/Anthropic 服务；相应协议测试使用本地 HTTP 假服务。原始记录与时延在 [本轮评测报告](eval/runs/2026-09-17-coding-review/REPORT.md)。

```bash
cargo test --offline --manifest-path core/Cargo.toml
cargo test --offline --manifest-path engine/Cargo.toml

bash review/eval/check-runner.sh
python3 tui/scripts/pty_smoke.py

```

本轮 PTY 使用临时 `XDG_CONFIG_HOME` 与 `XDG_STATE_HOME`，测试模型指向本地不可用端口，避免终端交互检查依赖外部模型；真实任务则使用用户已有模型配置与独立临时状态/工作目录。

已有固定任务是契约及冒烟检查：Rust 修复任务很小、验收测试可被模型看见。通过这些检查能够排除明确回归，不能外推为复杂仓库任务成功率，更不能代替与竞品的公平对照。官方功能资料的来源与具体对照见能力审查报告。

## 继续达到目标的实施顺序

默认优先复杂编码任务完成率与长任务稳定性。以下是具体的下一阶段工作及完成标准，不把新产品范围记为已授权决策。

1. **建立仓库级编码基准。** 覆盖多文件缺陷、需求实现、重构、陌生仓库定位、脏工作区、长输出、上下文压缩、取消恢复、并行合并。隐藏验收保存在 Agent 可编辑目录之外，在完成后独立执行；同时检查原有测试和用户改动。固定源码版本、模型配置、时间/Token 预算，每项至少运行 3 次。优先记录可验证完成率，再记录成本、耗时、人工干预和不必要改动。详细执行设计在能力审查报告。
2. **补足可审查的交付。** 基于实际工作区与明确基线展示全部变更，包含 Shell/Codex 修改；最近一次编辑回执只作为工具活动。完成标准：多文件、多批次、恢复与外部后端修改都能检查，用户原有脏改动被识别，验收结果与对应产出一致。
3. **扩展长任务与工具环境验收。** 用真实任务验证压缩后约束保留、失败后修正、恢复无重复副作用、多成员冲突处理，以及 Python/Node 工程在沙箱中的构建与测试。新增终端会话/交互 stdin、跨会话记忆、跨平台等能力应先形成接口与权限方案，再确认与原计划的差异。
4. **运行竞品对照。** 可使用同模型的产品按相同模型比较；无法保持模型相同时单列“整产品配置”，不可混成框架优劣结论。只有在具有代表性的重复任务上达到完成率且无安全/数据损坏回归，才能给出“达到”判断；“超过”必须同时指明在哪类任务、何种模型和资源条件下成立。

当前不建议为了对齐功能清单引入插件市场、新框架或大规模架构改写。先消除错误完成、文件半写、失效取消与失真的评测结果，才能让后续能力投入可测量。

用户已选择复杂编码与长任务稳定性，后续实现与原生上下文模型验收见 [第二批改进](complex-coding-2026-09-17.md)。模型评测一律使用模型原生上下文长度，约定见 D-36；当前离线基线见 `docs/ACCEPTANCE.md`。
