# 持久对话完整性与长历史遍历修复（2026-09-19）

本轮在 D-26/D-28、D-32/D-35 的既有恢复与长任务范围内，修复历史恢复静默丢失、
损坏树的无界遍历及清空分支后的压缩根节点错误。只修改 engine 的 Chat 历史读取、
内部回退结果传播和相应回归；持久 JSON 格式、线程身份、团队事实、工具权限与模型配置不变。

## 已复现的问题

1. `load_history` 把无法读取、JSON 无效、根类型错误或线程不是消息数组都当成空历史。
   当 JSON 外层合法、目标线程结构无效时，`save_history` 后续仍能写入，
   导致新模型请求丢失原任务并覆盖原记录。生产 `open_session` 的回归已先失败于
   “不应发起模型请求”的断言。JSON 整体截断时，旧写入路径可能另外报错，
   因此不把所有损坏形态都说成原来会成功请求模型。
2. `load_tree` 只做反序列化，没有验证 leaf、父节点、重复 ID 或摘要跳转。
   无效 leaf 会静默得到空路径；循环父引用可能使原来的 `while` 永不结束。
   回退列表还用 `unwrap_or_default` 把读错隐藏成空列表。
3. `materialize` 和 `rewind_points` 沿每个节点反复从数组头查找父节点，长链为平方级遍历。
4. `/rewind 0` 后另起分支并压缩时，旧实现固定保留数组第一个 system 节点，
   会让新摘要跳到已放弃分支的根。独立旧代码副本中，新回归实际失败：
   `skip_to = n1`，当前分支根应为 `n4`。

[证据目录](eval/runs/2026-09-19-history-integrity/REPORT.md)。
初始恢复探针误读了 `TurnRun.error`（错误实际位于事件载荷），校正后才取得产品失败证据；
旧代码副本首次构建漏了编译期引用的配置样例，补齐后才得到上述分支断言失败。
这两次探针错误均单列保留，不计作产品缺陷。

## 实现

- 只有文件或线程不存在才按新对话处理。读取、解析和消息结构错误返回带文件路径的错误；
  不把原文放进错误消息，不写空树来替代损坏的线性历史。
- 读取和保存树时验证消息、非空且唯一的 ID、leaf、父节点的追加顺序和摘要祖先关系。
  使用迭代遍历检查摘要目标，没有按历史深度递归，也不逐个摘要反复爬全链。
  不猜测损坏记录的“正确”顺序或删除无法理解的分支。
- 展开模型消息、列回退点和生成工具读回索引共用从尾到头的线性祖先扫描。
  压缩的 `skip_to` 仍只影响模型展开；回退列表、读回及旧分支保留语义不变。
- 压缩保留当前物理分支的 system 根。稀疏导入 ID 不再与新追加节点碰撞；
  `rewind_epoch` 耗尽时，在移动 leaf 前报错，避免失败回退半生效。
- `AgentRunner::rewind_points` 改为内部 `Result`，经 session/worker 现有错误回执传出。
  正常 `rewind_points` 的 JSON 形状不变。损坏恢复走已有 `CheckpointError / OUTCOME_UNKNOWN`，
  在模型请求或工具副作用前停止，原文件逐字节保留。

校验面向持久结构，不是历史内容的真实性认证；已存在且结构合法的内容改写无法仅凭 JSON 识别。
当前运行器缓存的历史仍沿用单写者约定，本次不提供运行中外部编辑器并发写入检测、自动修复
或磁盘配额。旧版本曾生成的跨分支摘要跳转会被明确拒绝，不能悄悄当作新对话继续。
