## R22 v2 上下文压缩（A20）落码记录

方案依据 §4.3/§7/§8 与 D-28 的 L2 契约；落码形如 P5 设计稿，两处实现细节按下述理由调整。

**存储**：`V2_SCHEMA_VERSION` 1→2（`models.rs`）；`context_entries.compressed_by`（NULL=可见）、
`model_requests.kind`（'turn'|'compression'）。`store::open` 对 v1 库走单事务迁移分支
（DDL + 版本戳同事务，中途崩溃只会停在旧版本），其余版本仍拒绝打开（A34）。

**core 三命令**（`core/src/v2/control.rs`）：
- `begin_compression`：复用 `budget_goal`（A18 目标归属）与 `goal_deadline_passed`（A35）闸门 +
  `reserve_budget`，插入 `kind='compression'` 的 PENDING 请求；**不翻 phase、不 bump revision**
  （压缩不改变执行位置，单写者仍是发起它的那次回合），事件 `compression_began`；
  预算/截止拒绝是已提交结果（与 begin_request 同款，不丢审计事件）。
- `compress_context`：单事务——重标覆盖段 `compressed_by=新摘要 id`（旧摘要条目同样被覆盖）、
  追加 `kind='summary'` 条目（`refs_json` 带 `covers_to/covered/request_id/attempt_id`）、
  关闭请求（COMPLETE）并 `release_reservation`，事件 `context_compressed`。
- `fail_compression`：FAILED + 释放预留 + 事件；**不碰实例**（幂等，重放只报 already_closed）。
- 附带：`append_context` 的 refs 参数改为 JSON（摘要需要结构化来源），并拆出返回条目 id 的
  `append_entry`；epoch 关闭路径（`close_epoch_execution`）本就会取消 PENDING 请求并释放预留。

**driver**（`engine/src/v2/driver.rs`）：`over_threshold` 移植 v1 阈值
（`max(真实上次 prompt, 本次估算) > min(window−reserve, window×0.9)`，reserve=min(max_tokens|8192, window/4)），
真实用量从 COMPLETE 尝试缓存（重启后从库里读一次，回合路径不再多一次存储往返）；熔断 3 次；
触发点在 `step_ready` 的 begin_request 之前，成功后重读条目重建请求；压缩调用**单次不重试**，
COMPLETE 后 `record_attempt` 照常结算进目标预算并落制品；失败/空摘要→ `fail_compression` + 熔断；
`recover()` 把崩溃遗留的 PENDING 压缩请求按 fail_compression 收尾（摘要可安全重做）；
视图改为 `compressed_by IS NULL ORDER BY (kind='summary' DESC, idx)`（可见摘要至多一条且在保留尾部之前）；
`execute_readback` 改读整段 epoch，**压缩后原文仍可被 readback 取回**。

**两处实现细节调整（与 P5 设计稿不同，理由记录于此）**：
1. `compress_context` 收 `keep_ids`（保留可见集）而非 `covers_to` 前缀：D-28 的尾部保留本身可能是
   非连续片段（超大最新输入 + 之后若干完整 assistant 组），前缀模型无法表达。
2. **不移植 v1 的尾部尺寸截断**：实测按 v1 规则（`recent.truncate(1)` + 适配组）会在回合中途
   把该回合刚产出的 tool_call/回执一并覆盖（本机探针：`covered=2` 含当回合 assistant+tool 结果），
   模型随即看不到自己刚拿到的回执。改为「保留最新用户输入及其之后的全部条目」：摘要只覆盖上一回合
   留下的内容，当前工作集永不被遮蔽；代价是单回合自身流量超过原生窗口时压缩无能为力，
   该天花板写成 `ponytail:` 注释（§7 禁止把真实窗口改小来"优化"）。

**测试**：core 3 项（视图覆盖/原文可达/预算与截止闸门/迁移）+ engine 2 项（超窗压缩→计费→
重启后压缩态保留→readback 取回被覆盖回执；摘要失败回退不压缩 + 3 次熔断）。

## 附带发现并修复：校验完成后多出一回合、二次 finish 卡死

**现象**：带 `required_checks` 的目标通过后，`goal_completed` 之后 driver 仍会再起一回合
（探针事件序：`... goal_completed → request_began → attempt_recorded → response_imported`）。原因：
check 回执由 `consume_if_closed` 追加进上下文，成为可见尾部条目，而 `step_ready` 的闲置判据是
「最后一条是 assistant」——于是运行时的验收回执被当成待模型处理的工作。

**后果**：① 每个走校验的目标完成时多一次模型调用（浪费预算）；② 若模型在那一回合再次 `finish`，
`complete_goal` 返回 already_closed 且不再改 phase，实例永久停在 `COMPLETION_PENDING`
（探针：事件数 400ms 内不再增长、`phase=COMPLETION_PENDING`，新输入只能落库不被处理）；
③ 两个既有测试（`v2_driver::required_checks_pass_settles_the_goal`、
`required_checks_exhausted_parks_the_goal_blocked`）在该窗口内断言 phase，实测并行跑约 1/8 概率红。

**修复**（§8「完成只提出一次」的落地，不是方案外行为）：`complete_goal` / `block_goal` 在关闭目标时
同事务追加一条运行时署名的 assistant 条目（`runtime: goal <id> closed as <status>` / `blocked: <reason>`，
envelope_id 固定故重放幂等），尾部因此是 assistant → 实例恢复闲置，不再多起回合；
两个命令的 already_closed 分支补上「terminal 目标不得把实例留在 COMPLETION_PENDING」；
driver 的 `step_completion` 先查目标是否仍 ACTIVE，已终态则走 `close_completion` 收尾该回合。
证据：core `a_closed_goal_states_its_close_and_settles_a_late_finish`、
`a_blocked_goal_states_the_block_and_frees_the_instance`；engine `required_checks_pass_settles_the_goal`
（脚本加第二次 finish + 断言 goal_completed 后无 request_began、phase READY）。

## P5-c A32 负载点测量（证据与观察）

探针：`cargo run --offline --manifest-path engine/Cargo.toml --example rebuild_p5_load -- review/tmp/r2-p5-load`
（必须给全新目录；raw report 在同目录 `report.json`）。合成 250 步 × 20KB 文本经生产控制面写入，
含每步完整回合四命令（submit_input→begin_request→record_attempt→import_response）。

| 指标 | 数值 |

| 追加（`submit_input`） | p50 5.4ms，p95 8.2ms（WAL + synchronous=FULL，含命令回执写） |
| 整步四命令 | p50 9.2ms，p95 13.0ms |
| 请求构造（`prepare_request`，501 条消息/5.02MB 线稿） | p50 397ms（含 L1 遮蔽与 `estimated_tokens`） |
| 库增长 | 10,653,696 字节（每步 42.6KB，载荷 20KB；每步未复制历史，探针内断言 growth < payload+8MB） |
| 重开（`store::open` 校验格式/版本） | 1.3ms |
| daemon 历史页（200 条 / 4MB） | p50 24.3ms |
| 并发读 1/4/16 | p50 29.8ms / 45.6ms / 256ms（wall 30.3ms / 55.5ms / 274.6ms） |
| peer 实例页 | 3 条 / 213 字节（不触碰大实例历史） |
| RSS | 追加完成 9.1MB；16 并发读峰值 124.2MB |

同一二进制连跑两次，除首轮受编译/页缓存影响的项外（追加 p50 5.4–6.2ms、整步 9.2–12.3ms），
库增长、请求构造、页面与并发读的量级稳定；单次本机探针只作量级证据，不构成基准。

观察（不改行为，记入 P6/R24 候选）：

1. **请求构造 375ms 含第二次全量序列化**：`KernelInstance::prepare_request` 用
   `estimated_tokens(&json!({"messages","tools"}))` 重新拼装并序列化整份请求（5MB），P0 原型同字节数的
   纯 JSON 构造只要 101ms。1M 级窗口下这是每回合固定本地开销；P6 可改为按条目增量估算（需先确认估值
   变化对阈值/预算的影响）。
2. **读命令经 `Control::submit` 会把整页结果当回执存库**：一次 200 条历史页（4MB）在 commands 表写
   2,007,040 字节。daemon 读面走独立只读连接不产生回执（§9 生产路径正确），但任何经 Control 的读
   调用都会放大磁盘；若后续 CLI/工具要读大页，应先读回执存储策略。
3. **第二个写连接会 `database is locked`**：用 `Control::open` 在两个连接上并发提交命令（各写命令回执）时，
   deferred→write 升级冲突不受 `busy_timeout` 覆盖（实测 5s 后失败）。与 §4.1「同库单写者」一致：
   生产写入口只有 daemon 的存储工作者，读面用只读连接；探针并发读因此按 daemon 形状实现。
