# TeamAgents Rust 原生重构：逐项设计复核

日期：2026-09-23。范围：[R2 实现方案](../docs/TeamAgents-Agent-System-Rebuild-Plan.zh-CN.md) 的设计决策，不是对尚未实现代码的验收报告。本轮只修改文档，没有执行重构、真实模型评测或数据清理。

> 补记（2026-09-24）：本文写于重构前，正文引用的 v1 文件（`engine/src/chat.rs`、`tui/src/worker.rs` 等）
> 已在 R29 退役；对应的 v2 实现见 `engine/src/v2/`、`core/src/v2/` 与 `tui/src/v2app.rs`，
> 下文保留原文以记录当时的判断依据。

结论：**Rust 原生方案与已确认需求匹配，但“更少的框架”不是充分的性能证据。** 真正应保留的是短的模型决策路径、一个权威状态来源、明确的副作用边界；不能把 LangGraph 换成更大的自研通用框架。以下 45 项分别列出理由、成本、替代方案和改变选择的条件。

## 1. 证据与判断边界

- 需求依据是本轮 19 项答复，以及用户明确选定“Rust 小型 kernel + Rust 持久化实例运行时 + SQLite + 独立工具进程管理 + Rust TUI”。已确认项见方案 Q1–Q19 和 [D-42](../docs/DECISIONS.md#d-42-rust-原生-agent-系统重构方向2026-09-23)。具体工程机制不冒充用户逐项批准。
- 现有产品已经是 Rust：模型循环在 `chat.rs`，SQLite 在 [storage.rs](../core/src/storage.rs)，TUI 通过 `worker.rs` 使用 JSON 协议。此次不是把正在运行的 Python harness 翻译成 Rust；旧名称也不是运行时依赖的证据。
- 现有 [engine 依赖](../engine/Cargo.toml) 包含同步 ureq，[core 依赖](../core/Cargo.toml) 包含 bundled rusqlite，[TUI 依赖](../tui/Cargo.toml) 包含 ratatui。改异步 HTTP 有真实适配成本，也必须检查行为是否改变。
- [旧评测分析](terminal-bench-design-analysis-2026-09-23.md) 已指出永久错误重派、验证环境、完成证据、时限和轨迹等问题。998 次失败是调度风暴，不是 998 次模型推理；单 Leader 执行也不是失败原因。历史机械分数不能成为干净的新架构基线。
- 本轮没有本地 CPU/RSS/吞吐实测，也没有新成功率数据。表中的“保留”指有需求或机制依据；“候选”指需要探针选定；“删除”指从 R1 或不必要的设计扩展中去除。R/A 编号均对应方案中的实施任务与验收场景。

R1 修订前副本在本轮临时目录留存，SHA-256 为 `a83f3c7745e04d0e7c5ad1bd15ad3d37ab1c2c61dd1eddaabd78ce083a8a8fa5`；该临时副本不作为长期实施依赖。以下记录已完整说明主要撤销项。

## 2. 语言、框架与模块

| 编号 / 决策 | 本轮结论及充分理由 | 成本、备选与改变选择的条件 | 验证 |
|---|---|---|---|
| RV-01 Rust kernel | 保留，用户已选定；与宿主、工具和 TUI 同语言，边界可以直接用 Rust 类型表达 | Python 对实验迭代有优势；网络/模型耗时大时语言差异可能很小。不能承诺换语言提高推理能力，也不把既有 Rust 投入当作唯一理由 | R02/R04；同可靠性本地开销测量 |
| RV-02 去掉 LangGraph | 删除框架依赖；所需闭环有限，领域权限、操作账本和后台进程仍需自己实现，框架尚无不可替代职责 | 自研承担恢复正确性。若未来出现大量用户定义工作流，且框架能以一个权威存储替代现有机制，再重新比较；现在不预建兼容层 | R01/R03；A06–A11 |
| RV-03 小 kernel + 显式状态机 | 保留；请求/响应转换与外部执行分离，通信拓扑不进入执行解释器 | 任意图不意味着任意控制流。通用 actor/workflow 框架或插件型 kernel 会新增生命周期；裸 while 循环又不足以表示恢复位置。首版采用有限 phase 和独立可运行状态 | R05/R09；A01/A02/A24 |
| RV-04 三 crate 与有限接口 | 保留 core/engine/tui，先分模块；kernel 不接数据库、网络或全局注册表 | 不以“不考虑重构成本”为理由重写所有经过验证的组件。实际出现独立发布/多客户端共用协议需求时再拆 crate；不用每名词一 trait | R01/R05/R19；检查依赖方向和协议样本 |
| RV-05 Tokio / 异步 HTTP | 有理由的候选：长连接、流、定时器与控制并存，需要及时让出执行权 | 新依赖及解析适配必须付出成本；有界阻塞线程若满足取消、控制响应、RSS，同样可用。丢弃 future 不等于停止阻塞工作或杀进程 | R02/R04；阻塞流期间控制响应、1/4/16 负载；A13/A28 |

模型侧应简洁，系统内部仍需可靠性代码；两者并不矛盾。额外机制必须能对应一个已确认需求或已观察故障。操作系统类比只用于说明实例、权限和通信：不照搬内存分页、驱动模型、通用系统调用表或调度算法。

## 3. 存储与持久化

| 编号 / 决策 | 本轮结论及充分理由 | 成本、备选与改变选择的条件 | 验证 |
|---|---|---|---|
| RV-06 每会话 SQLite | 保留；本机、单用户、会话隔离与清理边界一致，短事务足够表达所需原子更新 | 单库只有一个写者；大量会话有连接/维护成本。全局单库只有出现跨会话事务需求才更合理；Postgres 对多机/多租户有价值，首版无此需求 | R03/R09；A29/A31/A32 |
| RV-07 业务状态与执行位置同库 | 改为单一权威；消息应用、上下文和推进位置可同事务提交，删除 R1 双库握手 | 不是把模型/工具 I/O 放进事务。两个库会把内部一致性变成分布式提交问题；只有真正独立的事务域才值得分开 | R09/R10；A06/A08/A23 |
| RV-08 WAL + FULL | 保留，并显式配置；可靠性要求覆盖系统崩溃后的已确认提交 | 增加同步延迟，不能与 NORMAL 混用后宣称性能更优；批量非关键预览可减少开销，执行边界不能省略。部署必须用已验证本地文件系统 | R02/R03/R04；进程故障和系统故障分列 |
| RV-09 追加历史 + 小执行位置 | 保留；1M 上下文不应每步完整复制、落盘 | 纯快照最简单但写放大大；全量事件溯源增加重建和版本兼容成本。事件用于投递/审计，关系状态用于权威查询，不要求从全部事件重算世界 | R08/R09；A20/A32 |
| RV-10 不可变制品 | 大内容采用引用，小结构留 DB；发布文件后再提交引用，恢复不会读到尚未落盘的对象 | 比全 BLOB 多 GC/访问校验；哈希不是权限。先验证阈值和文件数量，若大 BLOB 在目标负载下更简单且可接受，可调整存储布局而保持原子契约 | R03/R08；A30/A31/A32 |

SQLite 的 WAL 单写者、本地共享内存限制及跨库原子性边界见[官方文档](https://sqlite.org/wal.html)；FULL 的持久性区别见[同步选项](https://sqlite.org/pragma.html#pragma_synchronous)。这些事实支持上表的约束，不证明本项目已经达到吞吐或断电恢复目标。

## 4. 操作、进程与生命周期

| 编号 / 决策 | 本轮结论及充分理由 | 成本、备选与改变选择的条件 | 验证 |
|---|---|---|---|
| RV-11 稳定操作身份与回执 | 保留；同一模型决定产生的工具调用可以识别、复用结果，内部消费去重 | 不能把本地 SQLite 事务延伸到任意远端服务。远端有可信幂等键时才采用其恢复语义；否则未知结果核验/停放，不许诺 exactly-once | R10/R11；A08/A09/A25 |
| RV-12 单 daemon 锁与实例执行槽 | 用 OS 锁、单写上下文和 revision 取代额外执行租约层 | 单机无须时钟抢主、租约续期或共识；锁 FD 继承会阻止重启，必须测。未来多机才需要重新设计主权和 fencing | R03/R09；A24/A33 |
| RV-13 按需 Shell runner | 保留独立进程管理，但只给需跨后台生命周期的命令；复用同一 Rust 二进制 | 每实例一个进程或每工具一个进程会增加无关开销；常驻通用 job 服务是另一个服务边界。若大量短命令的进程成本成为瓶颈，再比较 runner 池，不能牺牲身份/恢复隔离 | R03/R11；A11/A12/A32 |
| RV-14 READY/GO 与未知启动窗口 | 增补握手、唯一 job 锁和持久化接受标记；执行先获授权，重复派发可核对 | OS 进程创建与 DB 不能做原子事务；接受后未记录 PID 的崩溃窗口仍需未知状态。只看到 PID 缺失或进程消失不能安全重做 | R03/R11；A09–A11 |
| RV-15 模型请求与流恢复 | 一个组件掌握传输重试；完整响应才产生可执行意图，partial 只留证据 | 模型请求重发也可能重复计费；完整响应先落制品可减少重推理。除非供应商支持可核验的请求恢复，不假定重试复现同一采样结果 | R05/R10/R12；A18/A19 |
| RV-16 暂停、取消、界面退出、停机 | 明确区分；用户关闭 TUI 不取消任务，停止后台也不偷偷清理成功命令的服务 | 把所有情况映射成 abort 很简短但违反需求。full_auto 只承诺当前受控进程组，脱离组的进程不是自动终止对象；cgroup 增强须作为独立需求评估 | R11/R12/R19；A12/A13/A35 |
| RV-17 实例、任务与 epoch | 分离生命周期；实例复用而调用固定归属一个 goal；reset 不复用身份/上下文代次 | 只有一个 status 会混淆任务取消和已发生副作用。也不需要无限层嵌套“agent 内 agent”；短期助手复用同一实例机制 | R13/R16；A18/A21/A24 |

Tokio 的已启动 `spawn_blocking` 任务无法靠 abort 中止，见[官方 API 文档](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)。这只是否定一种取消假设；Shell 的真实终止与 runner 存活需要实际进程测试。

## 5. 权限、通信与模型可见面

| 编号 / 决策 | 本轮结论及充分理由 | 成本、备选与改变选择的条件 | 验证 |
|---|---|---|---|
| RV-18 限定能力与下授 | 保留；用户要求管理权可部分下授，运行时检查，父授权撤销有明确后果 | 仅 Leader/Worker 两角色不足以表达要求；但无须策略 DSL。首版仅实现当前动作、资源范围和父授权关系，拒绝无法表达的扩大授权 | R14；A03/A04 |
| RV-19 通信边与授权一个来源 | 改为边是 grant 的视图/引用，删除双 ACL | 独立 channel ACL 和 capability ACL 易出现撤销不一致。channel_id 可以是稳定标识，不应成为第二条授权途径 | R14/R15；A02–A05 |
| RV-20 Leader 与用户地位 | Leader 是默认获管理权的普通实例；用户有全局视图，Agent 不自动继承 | 硬编码超级 Leader 会破坏私有上下文。若未来多用户，需要单独设计用户权限；不把当前单用户 TUI 权力扩展成所有模型的权力 | R13/R14/R19；A05/A21 |
| RV-21 默认共享项目 | 保留用户选择；需要修改同一项目时省去不必要的合并和复制 | 会产生并发文件冲突；目录/worktree 是按需方案。受控写入用版本前置检查，Shell 无法从字符串证明无冲突，不承诺全面文件事务或同用户强隔离 | R07/R15；A05/A17/A29 |
| RV-22 持久消息、背压与等待 | 保留；消息与上下文应用去重，等待注册和检查已有结果原子化 | 通信环不是死锁；ALL/ANY、计时器和外部操作必须参与判断。只诊断有证据的封闭等待，不建设通用自动拓扑优化器或靠超时猜测所有等待都是失败 | R15/R16；A06/A22/A23/A28 |
| RV-23 用户直接干预实例 | 保留；安全边界接收输入，通知任务状态变化，私有对话不自动转发 | 用户与 Leader 同时修改任务需 revision/归属检查。不能另起一个修改同一历史的聊天循环，也不能因干预将旧操作账单转给新目标 | R13/R19；A21/A24 |
| RV-24 少量直接协作动作 | 合并常规 spawn+初始任务+返回路径；少做机械管理回合，基础工具保持直接 | 不能只减少工具名字而扩展一个庞大 JSON 分支协议。高级管理按权限暴露，MCP/Skills 按需发现；到底节省多少 Schema token、错误调用和任务成本需要测 | R05/R13/R18/R24；A01/A02 |
| RV-25 一次完成申请与按需审查 | 保留简单 finish，系统关联已有证据；没有理由要求每题多一个 reviewer | 多一轮模型肯定不是客观验证；完全自由的最终文本又无法触发必需检查。独立审查可在高不确定任务使用，费用计入原目标 | R20/R24；A01/A16 |
| RV-26 检查来源与有效期 | 增补要求来源、产物版本、环境和观察时间；取消实现子任务不能删除原目标要求 | 模型编出的检查不等于用户批准的契约；任意外部世界也不能全量哈希。只对声明依赖保证失效检测，其余如实列为未验证或需重新探测 | R07/R20；A15–A17 |

“隔离”在这里有准确边界：私有模型历史和受控接口权限是运行时契约，共享项目是明确资源，full_auto 是用户接受的主机访问。把每个实例包装成名为 kernel 的对象，不会自动获得操作系统级安全隔离。

## 6. 模型、工具、预算与调度

| 编号 / 决策 | 本轮结论及充分理由 | 成本、备选与改变选择的条件 | 验证 |
|---|---|---|---|
| RV-27 薄供应商协议层 | 保留多供应商及必要原生字段，协议类型与品牌分离 | 万能 SDK/统一消息模型可能丢字段，自写也可能漏协议细节。优先复用已验证解析样本；若某 SDK 明确保留所需行为且降低维护负担，可在适配器内采用，不让它掌握调度 | R05/R17；A19/A27 |
| RV-28 原生窗口与按需压缩 | 保留原生长度，压缩独立验证；输出、工具 Schema 和协议预留计入容量 | 缩成 16K/64K 会改变题目条件，不能称优化。1M 不代表每次都填满；压缩有遗漏风险和费用，收益与正确性必须单测/对照 | R05/R22/R24；A18/A20/A32 |
| RV-29 MCP 与基础工具同闸门 | 保留统一权限/批准/取消/回执；MCP 注解不作为自动重放证明 | 不可信或未验证服务的 idempotent/read-only 声明不是本地事实；不能通过套一个 runner 创造远端事务。已验证服务可配置具体恢复策略，按服务契约验收 | R18；A04/A09/A25 |
| RV-30 Skills 按需加载 | 保留注册根与搜索/读取，技能正文属于上下文，不是权限来源 | 全量注入扩大上下文和指令冲突；完全不加载又丢失用户要求的扩展能力。无需技能执行虚拟机或动态代码插件系统 | R18；A26 |
| RV-31 目标统一预算 | 保留；委派、压缩、重试和验证从同一预算结算，默认无目标上限 | 不设目标上限不等于无限重试或无资源边界。未知 usage/价格会限制硬金额保证；精确 token 限额与估算费用应分别呈现 | R12/R16；A07/A18 |
| RV-32 并发与公平性 | 撤回缺少基线的并发初值 4 建议；资源可配置，控制与回执不能饿死 | 越多并发不一定越快，会争预算、内存和工作区。以 1/4/16 为探针负载点，不是默认值；只有实测才决定是否需要更复杂调度或保留槽位 | R04/R16；A18/A28/A32 |
| RV-33 重复失败与无进展 | 硬处理已分类基础设施错误，语义进展线索交给模型/用户 | 相同测试重复执行可能正常，固定 N 次自动失败会误伤长任务。持续模型错误也需有界记录/停放条件，但不能把任意重复命令当作永久错误 | R12/R16；A07，正常修复循环回归 |

MCP 对工具注解的信任边界见[官方工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)。权限策略继续采用已确认的 approved_scope/full_auto，规范中的交互建议不改写用户已给出的授权。

## 7. 后台、界面、观测与升级

## 9. 本轮实际改掉的内容

相对 R1，删除 Python/LangGraph 后端、独立检查点数据库和框架图执行依赖；以本机锁和 revision 明确替代含糊的执行租约层，将 Channel 收敛为授权投影。撤回未经测量的并发建议初值和成绩区间门槛。独立进程的必要范围明确为 Shell 执行；保留并细化 R1 已有的上下文引用、直接协作动作和简洁完成申请。

新增或细化的边界包括：模型回复与工具意图原子入账、runner 启动未知窗口、批准/撤权的派发线性化点、制品发布顺序、ALL/ANY 等待和丢唤醒、实例重置后的迟到回执、后台评测截止、检查证据时效及新格式后续升级。

“足够简单”的验收应同时观察：模型初始指令和 Schema 成本、无效调用、任务必需之外的管理回合、每步存储/内存开销，以及故障恢复分支是否可测。代码行数或少一个库只能作为线索，不能作为性能结论。
